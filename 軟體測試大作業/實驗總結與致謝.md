# 五、實驗總結

被測系統：Automation Exercise（https://automationexercise.com）
測試範圍：功能黑盒測試（205 條）、Postman API 測試（14 支）、JMeter 效能測試（5 場景）、Selenium 瀏覽器自動化（6 流程）。

## 5.1 實驗遇到的困難與解決方法

| # | 遇到的困難 | 原因分析 | 解決方法 |
|---|---|---|---|
| 1 | Postman 對「無效登入」「方法不支援」等斷言一直失敗 | 該站 API **一律回 HTTP 200**，真正狀態碼放在回應 JSON 的 `responseCode` 欄位 | 斷言改為驗證 `pm.response.json().responseCode` 與 `message`，而非 HTTP 狀態列 |
| 2 | 用 Collection Runner 整跑時，「驗證登入(有效)」失敗 | 帳號類 API 有相依性，驗證/更新/刪除都需要先有帳號；但官方編號順序是 verifyLogin(API7) 在 createAccount(API11) 之前 | 重新排序為帳號生命週期：**建立→驗證→更新→查詢→刪除**，使單次由上而下即可全綠 |
| 3 | 重複執行時「建立帳號」回 Email already exist | 固定 Email 第二次就重複 | 在 createAccount 的 pre-request 用 `Date.now()` 產生**唯一 Email**，並於流程結尾刪除帳號，達到可重複執行 |
| 4 | JMeter 高併發場景（S4=100 緒）本機卡頓、出現少量錯誤 | 本機 CPU/記憶體與網路頻寬不足，連線數瞬間衝高 | 啟用「序列化執行緒群組」逐場景執行；高併發改**分批、降低執行緒數**重測，並在風險評估說明 |
| 5 | JMeter 各場景數據互相混入，截圖不乾淨 | Listener 會累積所有取樣資料 | 每場景執行前按 **Clear All** 清空，或逐一停用其他 ThreadGroup 只跑單一場景再截圖 |
| 6 | Selenium 點擊按鈕偶爾失敗 | 該站含 Google 廣告 iframe，會蓋住或攔截點擊 | 改用 `scrollIntoView` + JavaScript 點擊，並對彈窗/alert 做容錯處理；偶發失敗重跑即可 |
| 7 | Selenium chromedriver 版本與 Chrome 不符 | 手動下載 driver 容易版本對不上 | 採用 Selenium 4.6+ 內建的 **Selenium Manager**，自動下載相符 driver，免手動維護 |
| 8 | 205 條案例以人工逐筆維護易出錯、難統計 | 案例量大、欄位格式需一致 | 以 Python 產生器集中管理案例資料，一鍵輸出各模組 CSV 與彙總，並斷言總數=205 |
| 9 | CSV 在 Excel 開啟中文亂碼 | 預設編碼不含 BOM | 輸出採 **UTF-8-BOM**，Excel 直接開啟即正常顯示 |
| 10 | 安全性案例（SQL 注入 / XSS）難以自動斷言 | 需人工判讀是否外洩錯誤或腳本被執行 | 列為**手動驗證**重點，觀察登入應失敗、無資料庫錯誤外洩、腳本不被執行 |

## 5.2 品質評估
綜合功能、API 與效能測試結果：核心購物流程（瀏覽 → 搜尋 → 加入購物車 → 結帳下單）可正常運作，14 支 API 回應碼與訊息均符合官方文件規格，關鍵介面在中低併發下回應時間與吞吐量穩定。系統未發現致命缺陷，但在輸入驗證與安全性（注入/XSS 防護、邊界值處理）方面仍有可加強之處，建議修復一般缺陷後即可發布。

## 5.3 個人總結
- **收穫**：熟悉等價類劃分、邊界值分析、判定表與場景法等黑盒設計方法；學會以 Postman 撰寫自動化斷言、用 Collection Runner 批次執行；以 JMeter 設計多階段壓力測試並解讀 Aggregate Report；並透過 Selenium 將關鍵流程自動化、自動截圖。
- **不足**：自動化覆蓋率仍偏低（205 條中僅 6 條核心流程自動化）、效能測試僅針對少數不需登入的介面、安全性測試多依賴人工判讀。
- **後續可改進**：擴充 Selenium 覆蓋更多模組、為 API 測試串接 CI（Newman）、導入資料驅動測試以提升案例覆蓋。
